## 1. What are MCP-Based Tools?

The Model Context Protocol (MCP) is a **standardized, open protocol** for exposing tools, resources, and prompts to LLM applications — instead of every team hand-wiring their own bespoke `@tool` functions into every agent that needs them, MCP defines a common client-server contract so tools built once can be discovered and used by *any* MCP-compatible agent.

Every tool pattern so far in this series (Patterns 01–09) was implemented as an **in-process Python function** decorated with `@tool` and directly bound to one specific agent. That works, but it doesn't scale across an organization:

| Hand-wired tools (Patterns 01–09 so far) | MCP-based tools |
|---|---|
| Each tool is Python code living inside the agent's own codebase | Tools live in independent **MCP servers** — separate processes/services |
| To use a tool in a *different* agent, you copy/reimplement the function | Any MCP-compatible agent can discover and call the same server's tools without reimplementation |
| No standard way to advertise "what tools exist and what do they do" | MCP defines a standard `list_tools` discovery call with structured schemas |
| Tool versioning, ownership, and access control are ad hoc per-project | A dedicated team can own and operate an MCP server (e.g., "Case Management MCP Server") as a real service with its own deployment lifecycle |
| Adding a new tool means redeploying the agent | Adding a tool to an MCP server makes it available to every agent connected to that server, with no agent redeployment needed |

**Where this fits in the series:** MCP-Based Tools isn't a *new kind* of tool capability — it's a **transport and discovery standard** that can wrap any of Patterns 01–09 (a database query tool, a search tool, a calculator) and expose it over a common protocol. Think of Patterns 01–09 as "what kinds of tools exist," and Pattern 10 as "how tools get packaged, discovered, and shared across an organization's many agents."

---

## 2. What Problem Does It Solve?

| Problem | How MCP fixes it |
|---|---|
| Helios has many agents (Fraud Investigation Agent, Case Triage Agent, Compliance Reporting Agent) that all need access to the same case-management data | Build one MCP server exposing case tools; every agent connects to it rather than each reimplementing its own database tool |
| No standard schema format across different teams' tool implementations | MCP mandates JSON-Schema-based tool definitions, so any client can introspect any server uniformly |
| Tool ownership and lifecycle are unclear when tools are copy-pasted across codebases | An MCP server is a real deployable service with its own owners, versioning, and deployment — a genuine service boundary, not a shared code file |
| Connecting to third-party tool providers (e.g., a vendor's fraud-data MCP server) requires custom integration work per vendor | Any MCP-compliant server, first-party or third-party, is usable the same way — since the protocol, not the vendor, defines the interface |
| Hard to add authorization/observability consistently across many hand-wired tools | MCP servers are natural policy enforcement points — a single place to apply auth, rate limiting, and audit logging for everything that server exposes |

## 3. Realistic Production Problem — Helios Case Management MCP Server

**Context:** Helios currently has the Fraud Investigation Agent (Pattern 02) with its case-query tools (Pattern 04) hand-wired directly into its own codebase. As Helios grows, a second agent — a **Case Triage Agent** that automatically prioritizes incoming cases — also needs the same case data access. Rather than duplicating the database tool code, Helios stands up a dedicated **Case Management MCP Server** that both agents connect to as MCP clients.

**The ask:**

1. Build an **MCP server** (`helios-case-mcp`) that exposes the Pattern 04 database tools (`get_case_summary`, `get_recent_transactions_for_case`, `search_similar_cases`) via the standard MCP `list_tools` / `call_tool` interface, with the same authorization and audit guarantees Pattern 04 established.
2. Build an **MCP client integration** in LangChain/LangGraph so the Fraud Investigation Agent can discover and call this server's tools exactly like any locally-defined `@tool`.
3. Demonstrate that a **second, independent agent** (Case Triage Agent) can connect to the *same* server and reuse the *same* tools with zero code duplication.

## 5. Complete Request → Response Flow

1. **Server startup** — `helios-case-mcp` starts as an independent process, registers its three tools (each with a full JSON-Schema input definition, mirroring the Pydantic-derived schemas from Pattern 04) via the MCP `list_tools` handler.
2. **Agent startup** — the Fraud Investigation Agent's `MultiServerMCPClient` connects to `helios-case-mcp` (over stdio for local dev, or streamable HTTP for production) and calls `list_tools()` to discover what's available.
3. **Schema translation** — the MCP client library converts each discovered MCP tool definition into a LangChain-compatible tool object automatically — the agent code treats them exactly like Pattern 01–09's local `@tool` functions from this point on.
4. **Agent reasons and calls a tool** — e.g., during an investigation loop (Pattern 02), the agent decides to call `get_case_summary(case_id="CASE-3321", requesting_analyst_id="analyst-jsingh")`.
5. **Protocol dispatch** — the MCP client serializes this as a standard MCP `call_tool` request and sends it over the transport to the server.
6. **Server-side execution** — the server's `call_tool` handler routes to the actual `get_case_summary` implementation (identical logic to Pattern 04: parameterized SQL, row-level authorization, generic error messages).
7. **Response returns** over the same transport as a structured MCP tool result, which the client translates back into a normal LangChain `ToolMessage` for the agent's message state.
8. **Second agent, same server** — completely independently, the Case Triage Agent's own `MultiServerMCPClient` connects to the *same* `helios-case-mcp` server and calls `search_similar_cases` — reusing the exact same server-side code, authorization, and audit trail, with zero duplication.
9. **Centralized audit** — because both agents' calls flow through the one server process, all case-data access (from *any* agent, present or future) is logged in one consistent place, which is a meaningful operational improvement over Pattern 04's per-agent audit logging.

---

## 6. Why MCP-Based Tools Is the Right Pattern Here

- **Single source of truth for shared capabilities** — once Helios has more than one agent needing the same case data, hand-wiring the same tool code into each agent's codebase becomes a maintenance and consistency liability; MCP gives a clean service boundary instead.
- **Standardized discovery removes integration guesswork** — a new agent team at Helios doesn't need to read another team's source code to understand what case tools exist; `list_tools()` is self-describing.
- **Consistent policy enforcement** — authorization, rate limiting, and audit logging live in the server, applied uniformly to every client, rather than needing to be re-implemented correctly by every agent team.
- **Interoperability beyond Helios's own codebase** — an MCP server built this way can, in principle, also be connected to by third-party or vendor-side MCP-compatible tools/agents under proper access control, without a bespoke integration for each one.
- **This pattern composes with, rather than replaces, everything before it** — the actual tool logic inside `helios-case-mcp` is still exactly Pattern 04's parameterized-query approach; MCP is the delivery mechanism, not a replacement for good tool design.

### 7.2 Full Code — The MCP Server (`helios_case_mcp_server.py`)

```python
"""
Helios Case Management MCP Server — MCP-Based Tools Pattern
================================================================
Exposes Pattern 04's case-query tools via the standard Model Context
Protocol, so any MCP-compatible agent can discover and call them without
reimplementing the underlying database access, authorization, or audit
logic.

Run (stdio transport, for local dev / single-agent use):
    python helios_case_mcp_server.py

Run (streamable HTTP transport, for production / multi-agent use):
    python helios_case_mcp_server.py --transport http --port 8765
"""

from __future__ import annotations

import argparse
import logging
import os
from datetime import datetime
from typing import Optional

from mcp.server.fastmcp import FastMCP
from pydantic import BaseModel
from sqlalchemy import text
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker

logger = logging.getLogger("helios.case_mcp_server")
logging.basicConfig(level=logging.INFO)


def audit_log(event: str, **fields) -> None:
    logger.info("AUDIT | event=%s | %s", event, fields)


# --------------------------------------------------------------------------
# 1. Same result schemas and query logic as Pattern 04 — the underlying
#    tool implementation does not change; only its delivery mechanism does.
# --------------------------------------------------------------------------

class CaseSummary(BaseModel):
    case_id: str
    account_id: str
    status: str
    fraud_pattern: Optional[str] = None
    opened_at: datetime
    risk_score: int


HARD_TRANSACTION_LIMIT = 10
HARD_SIMILAR_CASE_LIMIT = 5

_DB_URL = os.environ.get(
    "HELIOS_DB_URL", "postgresql+asyncpg://helios:helios@localhost:5432/helios"
)
_engine = create_async_engine(_DB_URL, pool_size=10, max_overflow=5, pool_pre_ping=True)
_session_factory = async_sessionmaker(_engine, expire_on_commit=False)


# --------------------------------------------------------------------------
# 2. MCP server instance and tool registration
#    FastMCP turns a plain typed async function into a fully-described MCP
#    tool automatically -- the docstring and type hints become the schema
#    that list_tools() advertises to any connecting client.
# --------------------------------------------------------------------------

mcp = FastMCP("helios-case-mcp")


@mcp.tool()
async def get_case_summary(case_id: str, requesting_analyst_id: str) -> dict:
    """Fetch summary details for a fraud case (status, account, risk score,
    fraud pattern). Only returns data if the requesting analyst is
    authorized for that case's team."""
    query = text("""
        SELECT c.case_id, c.account_id, c.status, c.fraud_pattern,
               c.opened_at, c.risk_score
        FROM cases c
        WHERE c.case_id = :case_id
          AND c.team_id IN (SELECT team_id FROM analyst_teams WHERE analyst_id = :analyst_id)
        LIMIT 1
    """)
    async with _session_factory() as session:
        row = (await session.execute(
            query, {"case_id": case_id, "analyst_id": requesting_analyst_id}
        )).mappings().first()

    audit_log("mcp_tool_call", tool="get_case_summary", case_id=case_id,
              analyst_id=requesting_analyst_id, authorized=row is not None)

    if row is None:
        return {"error": "not_authorized",
                "detail": f"Case {case_id} not found or not accessible to you."}
    return CaseSummary(**dict(row)).model_dump()


@mcp.tool()
async def get_recent_transactions_for_case(
    case_id: str, requesting_analyst_id: str, limit: int = HARD_TRANSACTION_LIMIT
) -> dict:
    """Fetch the most recent transactions linked to a case's account,
    most recent first. Capped at 10 rows regardless of the limit requested."""
    safe_limit = max(1, min(limit, HARD_TRANSACTION_LIMIT))

    auth_check = text("""
        SELECT 1 FROM cases c
        WHERE c.case_id = :case_id
          AND c.team_id IN (SELECT team_id FROM analyst_teams WHERE analyst_id = :analyst_id)
    """)
    txn_query = text("""
        SELECT t.transaction_id, t.amount_usd, t.transaction_type, t.occurred_at
        FROM transactions t
        JOIN cases c ON c.account_id = t.account_id
        WHERE c.case_id = :case_id
        ORDER BY t.occurred_at DESC
        LIMIT :limit
    """)

    async with _session_factory() as session:
        authorized = (await session.execute(
            auth_check, {"case_id": case_id, "analyst_id": requesting_analyst_id}
        )).first()
        if not authorized:
            audit_log("mcp_tool_call_denied", tool="get_recent_transactions_for_case",
                      case_id=case_id, analyst_id=requesting_analyst_id)
            return {"error": "not_authorized",
                    "detail": f"Case {case_id} not found or not accessible to you."}

        rows = (await session.execute(
            txn_query, {"case_id": case_id, "limit": safe_limit + 1}
        )).mappings().all()

    truncated = len(rows) > safe_limit
    rows = rows[:safe_limit]

    audit_log("mcp_tool_call", tool="get_recent_transactions_for_case", case_id=case_id,
              analyst_id=requesting_analyst_id, row_count=len(rows), truncated=truncated)

    return {
        "case_id": case_id,
        "transactions": [dict(r) for r in rows],
        "truncated": truncated,
    }


@mcp.tool()
async def search_similar_cases(
    fraud_pattern: str, region: str, requesting_analyst_id: str, limit: int = HARD_SIMILAR_CASE_LIMIT
) -> dict:
    """Search closed past cases with a similar fraud pattern in the same
    region, scoped to what the requesting analyst is authorized to see.
    Capped at 5 results."""
    safe_limit = max(1, min(limit, HARD_SIMILAR_CASE_LIMIT))

    query = text("""
        SELECT c.case_id, c.fraud_pattern, c.region, c.resolution
        FROM cases c
        WHERE c.fraud_pattern ILIKE :pattern
          AND c.region = :region
          AND c.team_id IN (SELECT team_id FROM analyst_teams WHERE analyst_id = :analyst_id)
          AND c.status = 'closed'
        ORDER BY c.opened_at DESC
        LIMIT :limit
    """)
    async with _session_factory() as session:
        rows = (await session.execute(
            query,
            {
                "pattern": f"%{fraud_pattern}%", "region": region,
                "analyst_id": requesting_analyst_id, "limit": safe_limit,
            },
        )).mappings().all()

    audit_log("mcp_tool_call", tool="search_similar_cases", fraud_pattern=fraud_pattern,
              region=region, analyst_id=requesting_analyst_id, row_count=len(rows))

    return {"results": [dict(r) for r in rows]}


# --------------------------------------------------------------------------
# 3. Entry point — supports both stdio (simple, local) and HTTP (production,
#    multi-agent-capable) transports
# --------------------------------------------------------------------------

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--transport", choices=["stdio", "http"], default="stdio")
    parser.add_argument("--port", type=int, default=8765)
    args = parser.parse_args()

    if args.transport == "stdio":
        mcp.run(transport="stdio")
    else:
        mcp.run(transport="streamable-http", port=args.port)
```

### 7.3 Full Code — The Agent-Side MCP Client (`investigation_agent_mcp_client.py`)

```python
"""
Fraud Investigation Agent — MCP Client Integration
======================================================
Connects the Pattern 02-style investigation agent to the helios-case-mcp
server (and, for illustration, a second hypothetical sanctions-screening
MCP server) using langchain-mcp-adapters, so MCP-hosted tools are used
exactly like any locally-defined @tool.

Run:
    export ANTHROPIC_API_KEY=sk-...
    # Assumes helios-case-mcp server is already running (stdio or http)
    python investigation_agent_mcp_client.py
"""

from __future__ import annotations

import asyncio
import logging

from langchain.agents import create_agent
from langchain_anthropic import ChatAnthropic
from langchain_core.messages import HumanMessage
from langchain_mcp_adapters.client import MultiServerMCPClient

logger = logging.getLogger("helios.investigation_agent_mcp_client")
logging.basicConfig(level=logging.INFO)

SYSTEM_PROMPT = """You are the Helios Fraud Investigation Agent, using tools
provided by the Helios Case Management MCP server. Investigate thoroughly
before concluding. Always pass requesting_analyst_id exactly as given to
you by the calling analyst -- never invent or guess an analyst ID."""


async def build_investigation_agent(analyst_id: str):
    # MultiServerMCPClient can connect to several MCP servers at once,
    # merging their tools into one list -- this is what lets an agent
    # combine, e.g., case-management tools AND a separate sanctions
    # screening MCP server, without special-casing either.
    mcp_client = MultiServerMCPClient({
        "helios_case_mcp": {
            "transport": "stdio",
            "command": "python",
            "args": ["helios_case_mcp_server.py"],
        },
        # Example of a second, independently-owned MCP server being
        # composed in -- e.g. a vendor-provided sanctions screening server.
        # "sanctions_mcp": {
        #     "transport": "streamable_http",
        #     "url": "https://sanctions-mcp.internal.helios.example/mcp",
        # },
    })

    tools = await mcp_client.get_tools()
    logger.info("Discovered %d MCP tools: %s", len(tools), [t.name for t in tools])

    llm = ChatAnthropic(model="claude-sonnet-4-6", temperature=0)
    agent = create_agent(model=llm, tools=tools, system_prompt=SYSTEM_PROMPT)
    return agent, mcp_client


async def run_investigation(case_id: str, analyst_id: str, instruction: str) -> str:
    agent, mcp_client = await build_investigation_agent(analyst_id)
    try:
        result = await agent.ainvoke({
            "messages": [HumanMessage(
                content=f"Case: {case_id}\nAnalyst: {analyst_id}\nInstruction: {instruction}"
            )]
        })
        final_message = result["messages"][-1]
        return final_message.content
    finally:
        # Ensure the MCP client's underlying transport connections are
        # cleanly closed -- important for stdio subprocess cleanup.
        await mcp_client.close() if hasattr(mcp_client, "close") else None


if __name__ == "__main__":
    summary = asyncio.run(run_investigation(
        case_id="CASE-3321",
        analyst_id="analyst-jsingh",
        instruction="Summarize this case and check for similar past cases.",
    ))
    print(summary)
```

### 7.4 Second, Independent Client Reusing the Same Server

```python
"""
Case Triage Agent — a COMPLETELY SEPARATE agent/service that reuses the
SAME helios-case-mcp server, with zero duplication of the database tool
code shown in Pattern 04 or above.
"""

from langchain.agents import create_agent
from langchain_anthropic import ChatAnthropic
from langchain_mcp_adapters.client import MultiServerMCPClient

TRIAGE_SYSTEM_PROMPT = """You are the Helios Case Triage Agent. Use
search_similar_cases to find precedent and get_case_summary to assess
new incoming cases, then assign a priority: low, medium, high, urgent."""


async def build_triage_agent():
    mcp_client = MultiServerMCPClient({
        "helios_case_mcp": {  # identical server connection as the investigation agent
            "transport": "stdio",
            "command": "python",
            "args": ["helios_case_mcp_server.py"],
        },
    })
    tools = await mcp_client.get_tools()  # same three tools, same server, no code copied
    llm = ChatAnthropic(model="claude-sonnet-4-6", temperature=0)
    return create_agent(model=llm, tools=tools, system_prompt=TRIAGE_SYSTEM_PROMPT), mcp_client
```

## Key Takeaways

- MCP is a **transport and discovery standard**, not a new tool capability — it wraps existing tool patterns (Pattern 01–09) in a protocol that any compatible agent can discover and call.
- **One server, many clients** — building `helios-case-mcp` once and connecting multiple independent agents (Fraud Investigation Agent, Case Triage Agent) to it eliminates the duplication that hand-wired tools accumulate as an organization's number of agents grows.
- **Authorization, audit, and business logic live in the server**, not scattered across every client that happens to need the capability — a real architectural improvement, not just a convenience.
- `MultiServerMCPClient` lets an agent **compose tools from several independently-owned servers** (internal and third-party) into one unified tool list, without special-casing each source.
- This pattern is the natural evolution once Patterns 01–09's tools need to be **shared across more than one agent or team** — introduce it exactly at that point, not before, since a single-agent system doesn't need the added service boundary.
