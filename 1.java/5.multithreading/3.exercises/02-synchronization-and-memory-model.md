## Exercise 2.1 — The Lost Page-View (race condition) ★

**Scenario:** An analytics service increments a page-view counter from 100 request threads, 10,000 increments each.

**Starter**
```java
class ViewCounter {
    private long count;
    void increment() { count++; }
    long get() { return count; }
}
```

**Task**
1. Run 100 threads × 10,000 increments; print the result vs. expected 1,000,000.
2. Explain with the bytecode (`javap -c`) why `count++` is three operations.
3. Fix with `synchronized`. Measure time before/after.

**Prove it:** The broken version loses updates on at least 9 out of 10 runs; the fixed one is exact on 100 out of 100.

## Exercise 2.2 — Inventory Reservation (check-then-act) ★★

**Scenario:** Two customers add the last unit of a product to their cart at the same time. Overselling is not acceptable.

**Task**
1. Implement `Inventory.reserve(sku, qty)` as: `if (stock.get(sku) >= qty) { stock.put(sku, stock.get(sku) - qty); return true; }` using a plain `HashMap`. Reproduce overselling using 50 threads fighting over 10 units.
2. Fix with a single global `synchronized`. Measure throughput.
3. Improve with per-SKU locking (a lock object per SKU). Measure again with 1,000 SKUs and 50 threads.
4. Add `reserve` for multiple SKUs at once (a cart). Notice the lock-ordering risk (see 2.7).

**Prove it:** Total stock reserved never exceeds initial stock; per-SKU locking shows measurable speedup over global lock.

## Exercise 2.3 — The Shutdown Flag That Never Works (visibility) ★★

**Scenario:** A consumer loop polls a `running` flag. A management endpoint sets it to `false` to stop the consumer.

**Starter**
```java
class Consumer implements Runnable {
    private boolean running = true;
    public void run() { while (running) { /* poll */ } System.out.println("stopped"); }
    public void stop() { running = false; }
}
```

**Task**
1. Run it with an empty loop body (so the JIT can hoist the read). The loop may never stop. Try `-Xint` vs default and compare.
2. Fix with `volatile`. Then fix a second way with `synchronized` accessors, and a third way using interruption.
3. Write a paragraph in `NOTES.md` on the happens-before edge created by a volatile write → read.

**Prove it:** You can reproduce the hang reliably and show each fix terminating.

## Exercise 2.4 — Order-ID Generator (volatile is not atomic) ★★

**Scenario:** An order id generator uses `private volatile long next;` and `return ++next;`.

**Task**
1. Prove duplicates are generated by 20 threads × 100,000 calls (collect ids in a `ConcurrentHashMap.newKeySet()` and count duplicates).
2. Fix with `synchronized`, then (preview Group 4) with `AtomicLong`.
3. When *is* `volatile` enough? Implement a `volatile` immutable-snapshot configuration holder as the correct usage example.

**Prove it:** Zero duplicate ids; you can state the rule "volatile is enough when writes don't depend on the current value".

## Exercise 2.5 — Hand-Rolled Bounded Buffer (wait/notify) ★★★

**Scenario:** An email service buffers outbound messages between API threads (producers) and SMTP senders (consumers). Implement the buffer without `java.util.concurrent`.

**Task**
1. Implement `BoundedBuffer<T>` with `put()` (blocks when full) and `take()` (blocks when empty) using `synchronized` + `wait()`/`notifyAll()`.
2. Always wait in a `while` loop, not an `if`. Remove the loop and demonstrate a failure with multiple consumers (spurious wakeup / lost condition).
3. Replace `notifyAll()` with `notify()` and find the scenario where threads hang forever (producers and consumers waiting on the same monitor).
4. Run 4 producers, 4 consumers, 1 million messages. Verify no message is lost or duplicated.

**Prove it:** Sent count == received count, no deadlock after 10 runs; you can explain why `notify()` is unsafe here.

## Exercise 2.6 — Connection Pool Singleton (safe publication) ★★★

**Scenario:** A lazily-created `ConnectionPool` singleton is used across the app. First-use race conditions have caused two pools to be created.

**Task**
1. Write a lazy singleton without synchronization; show two instances created.
2. Write double-checked locking *without* `volatile`; explain the partially-constructed-object hazard.
3. Fix with DCL + `volatile`, then with the initialization-on-demand holder idiom, then with an `enum` singleton. Compare readability and guarantees.
4. Make `PoolConfig` an immutable `record` with `final` fields and demonstrate that final-field semantics give safe publication even through a data race.

**Prove it:** 1,000 threads calling `getInstance()` all see exactly one instance with a fully initialised config.

## Exercise 2.7 — Money Transfer Deadlock (intrinsic locks) ★★★

**Scenario:** `transfer(from, to, amount)` locks `from` then `to`. Two simultaneous opposite transfers (A→B and B→A) freeze the system.

**Task**
1. Reproduce the deadlock deterministically (use a `CountDownLatch` or `sleep` between the two lock acquisitions).
2. Capture it with `jstack <pid>` and read the "Found one Java-level deadlock" section.
3. Fix with global lock ordering (e.g. by account id). Handle the `from == to` edge case.
4. Fix again with a tie-breaker lock for equal ids/hash collisions (`System.identityHashCode`).

**Prove it:** 10,000 random concurrent transfers across 100 accounts; total money in the system is unchanged and the run completes.
